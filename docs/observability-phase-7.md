# Observability Phase 7: Distributed Tracing

Phase 7 adds backend-neutral distributed tracing to the five active Spring Boot applications. Micrometer Tracing bridges Spring observations to OpenTelemetry, applications export OTLP to an OpenTelemetry Collector, and the Collector batches traces into Grafana Tempo. Grafana is provisioned with Tempo, Prometheus, and Elasticsearch data sources so an operator can move from a slow trace to related metrics and logs without exposing observability tools to public users.

## Runtime flow

```text
Browser
  -> API Gateway
      -> Identity Service
      -> Post Service <-> Content Service
      -> Notification Service

Spring observations / Micrometer Tracing
  -> OTLP/HTTP -> OpenTelemetry Collector
      -> OTLP/gRPC -> Tempo
          -> Grafana Explore
              -> Prometheus metrics
              -> Elasticsearch application logs
```

HTTP server and client spans are created automatically. The Post and Content services build their `RestClient` instances from Spring Boot's managed builder, so W3C `traceparent` context is injected on service-to-service calls.

The asynchronous notification path uses an additional production pattern:

1. Post Service stores the event payload, correlation ID, `traceparent`, and optional `tracestate` in the same outbox transaction as the post.
2. The scheduled outbox publisher restores that trace context and creates a `post.outbox.publish` producer span.
3. Spring Kafka observation creates and injects the Kafka producer span.
4. Notification Service extracts the Kafka context and creates the consumer span.
5. The complete request, outbox relay, broker boundary, and notification processing can be inspected as one trace.

The existing `X-Correlation-Id` remains useful for customer support and manual searches. Trace IDs are generated by the tracing system and model the exact distributed operation; correlation IDs are stable application identifiers that may span retries or multiple traces.

## Components and retention

| Component | Purpose | Local access |
| --- | --- | --- |
| OpenTelemetry Collector `0.163.2` | Receive OTLP, apply memory limits and batching, export to Tempo | OTLP gRPC `4317`, OTLP HTTP `4318` |
| Grafana Tempo `3.1.0` | Store and query traces | `http://localhost:3200` |
| Grafana | Trace search, waterfall view, service graph, trace-to-logs | `http://localhost:3001` |
| Elasticsearch/Kibana | Search ECS logs by `traceId`, `spanId`, or `correlationId` | `http://localhost:5601` |
| Prometheus | HTTP/JVM/business metrics plus Tempo service-graph metrics and exemplars | `http://localhost:9096` |

The repository uses Tempo's local filesystem backend for Docker Compose and local Kubernetes demonstrations. This is deliberately not a highly available production store. A production deployment should use managed or replicated object storage, TLS between telemetry components, authenticated private access, capacity limits, and a retention policy based on traffic and compliance requirements.

## Start with Docker Compose

Rebuild the Java images because Phase 7 adds tracing libraries:

```powershell
docker compose up -d --build
docker compose ps
```

Verify the trace backend and Collector:

```powershell
Invoke-RestMethod http://localhost:3200/ready
docker compose logs --tail=50 tempo otel-collector
```

Generate traffic through the public boundary, for example:

```powershell
$response = Invoke-WebRequest -UseBasicParsing http://localhost:9090/api/posts?pageNo=0&pageSize=5
$response.StatusCode
$response.Headers['X-Correlation-Id']
```

Then open Grafana:

1. Sign in at `http://localhost:3001`.
2. Open **Explore** and select the **Tempo** data source.
3. Search with TraceQL such as `{ resource.service.name = "api-gateway" }`.
4. Open a result to inspect the gateway and downstream waterfall.
5. Select a span and use the logs link to query Elasticsearch for the same `traceId`.

For the Kafka path, create a post, wait for the outbox relay, and search for `post.outbox.publish`, `kafka.produce`, or Notification Service spans. The same trace should contain the original Post Service request and the consumer work.

## Search the same request in Kibana

Spring's tracing MDC fields are included in the existing ECS JSON logs. In the **Blog Platform Logs** data view, use KQL:

```text
traceId : "<trace-id-from-grafana>"
```

Other useful investigations:

```text
spanId : "<span-id>"
correlationId : "<X-Correlation-Id>"
service.name : "post-service" and log.level : "ERROR"
```

## Run with Kubernetes

The Kustomize base now deploys Tempo, the Collector, persistent local trace storage, and the provisioned Grafana data sources. After the normal local deployment:

```powershell
kubectl -n blog-platform get pods
kubectl -n blog-platform port-forward service/grafana 3001:3000
kubectl -n blog-platform port-forward service/tempo 3200:3200
```

Inspect telemetry delivery with:

```powershell
kubectl -n blog-platform logs deployment/otel-collector
kubectl -n blog-platform logs deployment/tempo
```

## Sampling and cost control

Local Docker and Kubernetes default to `TRACING_SAMPLING_PROBABILITY=1.0` so every demonstration request is visible. Production Compose defaults to `0.1`, which records approximately ten percent of traces. Change the probability based on request volume and incident needs:

```text
TRACING_SAMPLING_PROBABILITY=0.1
```

Head sampling is simple but can discard rare failures. A higher-volume production platform would evaluate tail sampling in the Collector, preserving errors and unusually slow traces while sampling routine successes more aggressively.

Do not attach secrets, JWTs, request bodies, email addresses, or post content as span attributes. The current instrumentation records framework-safe route and protocol metadata plus bounded outbox identifiers.

## Configuration validation

CI validates both Compose files, rendered Kubernetes manifests, and the exact Tempo and Collector configuration files against the pinned container images. The equivalent local commands are:

```powershell
docker run --rm -v "${PWD}/deploy/k8s/tracing:/etc/tempo:ro" grafana/tempo:3.1.0 "-config.file=/etc/tempo/tempo.yml" "-config.verify=true" "-config.verify-errors-only=true"
docker run --rm -v "${PWD}/deploy/k8s/tracing:/etc/otelcol-contrib:ro" otel/opentelemetry-collector-contrib:0.163.2 validate --config=/etc/otelcol-contrib/otel-collector.yml
```

## Troubleshooting

- **No traces in Grafana:** verify the application uses the Collector URL, inspect Collector logs, and confirm the selected time range includes the request.
- **Only one service appears:** call through the Gateway and ensure downstream HTTP clients are created from Spring's managed client builder.
- **Kafka trace is separate:** confirm the Post Service Flyway migration added `traceparent`/`tracestate` and both Kafka observation properties are enabled.
- **Trace-to-logs returns nothing:** wait for Filebeat indexing, expand the time window, and confirm the log document contains the top-level `traceId` field.
- **Service graph is empty:** generate traffic across at least two services, wait for Tempo's metrics generator to remote-write to Prometheus, and refresh Grafana.

## Interview explanation

> We instrumented the Spring Boot services with Micrometer Tracing and the OpenTelemetry bridge. Services export OTLP to a Collector rather than directly coupling to Tempo. Tempo stores traces, Grafana provides the waterfall and service graph, and trace-to-logs links a span to ECS logs in Elasticsearch. We also persisted W3C trace context in the transactional outbox, so delayed Kafka publication and consumption remain connected to the originating HTTP request. Local environments sample everything; production defaults to ten percent and would move Tempo storage to an authenticated object store.
